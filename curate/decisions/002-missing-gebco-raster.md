# The GEBCO raster was never missing — `area_h3` can be rebuilt

**Status: CLOSED — 2026-09-22. The raster is in `raw/aux/`; `h3_index.R` was looking
for a filename that was never created.**
**Raised: 2026-09-20. Reversed: 2026-09-22.**

## Resolution — 2026-09-22

The maintainer pointed at
`$FISHYDATA/raw/aux/gebco_2026_n89.0_s35.0_w-45.0_e69.0_geotiff.tif`. Verified: 709 MB,
extent `-45, 69, 35, 89` — exactly the requested bounding box — EPSG:4326,
12960 × 27360, opens with `terra::rast()`. It is the file this record said to
re-download, under the name GEBCO's download service gives it.

`h3_index.R:22` was repointed at that name rather than the data being renamed to
`gebco_2026.tif`: the bounding box in the filename **is** the provenance of the
request, and `AGENTS.md` says nothing under `$FISHYDATA` is hand-edited. The CANNOT RUN
banner is gone from the script, and `check_ready()` now reports `area_h3` as ready —
the only target it had been blocking.

**What actually went wrong is worth more than the fix.** The record never said "we have
a raster whose name does not match"; it said the file was *gone*, having "searched every
`.tif` under `$HOME`". The 2026-09-21 addendum then said `raw/aux` "contains no `.tif` at
all", while `TODO.md` item 6, written around the same time, located the original in
`~/Downloads/older/`. Two statements in the same record layer, contradicting each other,
both asserting absence — and the file was in the data store the whole time. A search
that reports "gone" is a claim about the searcher as much as the filesystem, and neither
statement was ever re-run.

**Rebuilt and gated, 2026-09-22.** `tar_make(names = "area_h3")` ran in 7m30s and wrote
668 MB. The gate in step 4 below passes on all four numbers — 26,160,965 cells, 66
`fao`, 27 `bbht`, depth −6002 to 4 — and a stronger check was run alongside it, because
matching summary statistics do not prove matching contents: an anti-join against
`raw/aux/h3_indices.parquet` in **both** directions returns zero rows, and `depth`,
`bbht` and `fao` disagree on **zero** cells.

The table is therefore no longer seeded. It is built, and the two independent facts that
fall out are worth separating: the seeded copy was **genuine** (nothing had silently
diverged from it), and the script **reproduces** it from the raster. Neither was known
before today; the pipeline had one table it had never made.

## Superseded — the original record, kept for the reasoning

## What is missing

`reference/geo/h3_index.R` reads a GEBCO gridded-bathymetry GeoTIFF. It is **not on this
computer**. Searched: every `.tif`/`.tiff` under `$HOME` and all mounted volumes, plus the
Trash. It is gone.

Its original location was a `~/Downloads` folder that has since been cleared:

```
~/Downloads/GEBCO_07_May_2026_8472de0f82f8/gebco_2026_n89.0_s35.0_w-45.0_e69.0_geotiff.tif
```

Firefox still holds a storage entry for `download.gebco.net` dated **2026-05-08**, the same
day `h3_indices.parquet` was built — so it was downloaded, used once, and cleared.

Note that `raw/aux/ICES_GEBCO.rds` and `staging/aux/gebco.gpkg` are **not** this dataset.
Those are the nine ICES depth-*class polygons*. `h3_index.R` needs the continuous-depth
raster.

## Why it matters

`area_h3` produces `curated/reference/area_h3.parquet` — **26,160,965 H3 resolution-8
cells** carrying `depth` (−6002 to 4 m), `bbht` (27 MSFD habitat classes) and `fao` (66 ICES
areas). It is the join key for all spatial tagging in the AIS chain: `ais_ping_tag.R` hashes
every ping to an H3 cell and looks it up here.

Until the raster is restored, **that table cannot be regenerated by any means**.

## What has been done

The single surviving copy has been duplicated so it is no longer only in `legacy/`, which is
destined for cleanup when the archives are retired:

| Path | Role |
|---|---|
| `raw/aux/h3_indices.parquet` | safeguard copy, treated as an unbuildable input |
| `curated/reference/area_h3.parquet` | seeded so downstream targets could run — **rebuilt 2026-09-22, identical** |
| `legacy/curated/aux/h3_indices.parquet` | the original, still in place |

`curated/reference/area_h3.parquet` is therefore **seeded, not built**. It is the one table
in the sweep that the pipeline did not produce.

*2026-09-22: no longer true — see Resolution above. It is built, and byte-for-byte
equivalent in content to the copy that was seeded.*

## What needs doing

   e69.0`, GeoTIFF format. A few GB.
2. Place it at `$FISHYDATA/raw/aux/gebco_2026.tif`, which is where `h3_index.R` now looks
   (it previously hard-coded the `~/Downloads` path).
3. `targets::tar_make(names = "area_h3")`.
4. Gate the result against `raw/aux/h3_indices.parquet`: expect 26,160,965 cells, 66 `fao`
   values, 27 `bbht` values, depth range −6002 to 4.

Until step 3 succeeds, `R/check_ready.R` will keep reporting `area_h3` as BLOCKED. That is
correct and should be left reporting.

## The general lesson

This is the only input in the pipeline that was neither a database dump nor a versioned
artifact — it was a manual browser download into a scratch folder, used once. Nothing
recorded where it came from or that it had gone. Worth checking whether any other input has
the same shape; the three GIS layers under `raw/gis/` and the PAME class-B archive are the
obvious candidates, though those at least still exist on the server.
